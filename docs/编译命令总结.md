# 编译命令总结

## 原则

- 借助 `buildroot` 进行 `zImage`、`dtb`、`rootfs` 编译，且不污染 Buildroot 源码。
- BSP 固化配置放在 `./bsp/configs/`，rootfs overlay 放在 `./bsp/rootfs_overlay/`，本地包放在 `./bsp/package/`。
- 以下命令默认在仓库根目录 `/home/friedegg/imx6_driver_friedegg` 执行。
- Buildroot 通用参数：

```bash
BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk
```

## 当前系统画像

主线 rootfs 已切换为 Buildroot internal toolchain + glibc + Qt5 Widgets/linuxfb。内核、DTB 和外置 `.ko` 继续使用 Linaro GCC 4.9.4；rootfs、测试程序、`imx6-monitor` 和 Qt5 应用使用 Buildroot GCC 13.x + glibc。

详细 ABI 边界、干净构建流程和板端验证见 `docs/qt5_glibc_system.md`。

## 新版 `build_and_deploy.sh`

入口脚本仍是：

```bash
./bsp/build_and_deploy.sh <subcommand>
```

默认不会再隐式执行“增量构建 + 全量部署 rootfs”。日常开发应明确选择子命令：

| 场景 | 命令 | 部署范围 |
| --- | --- | --- |
| 全量重编 | `./bsp/build_and_deploy.sh all` | TFTP: `zImage`/DTB；NFS: 全量 rootfs |
| 只改 DTS | `./bsp/build_and_deploy.sh dtb` | TFTP: DTB |
| 只改内核非 DTS 代码 | `./bsp/build_and_deploy.sh zimage` | TFTP: `zImage` |
| 只更新 rootfs | `./bsp/build_and_deploy.sh rootfs` | NFS: 全量 rootfs |
| 只改外部驱动包 | `./bsp/build_and_deploy.sh drv ap3216c` | NFS: 该包文件 |
| 只改摄像头驱动包 | `./bsp/build_and_deploy.sh drv ov5640_drv` | NFS: 该包文件 |
| 新增外部驱动包 | `./bsp/build_and_deploy.sh drv add <pkg> <src-dir> [app-bin]` | 生成 Buildroot external local 包 |

`NFS_DIR`、`TFTP_DIR`、`MAKE_JOBS` 可用环境变量覆盖：

```bash
NFS_DIR=~/linux/nfs/rootfs TFTP_DIR=~/linux/tftp MAKE_JOBS=8 ./bsp/build_and_deploy.sh drv ap3216c
```

## 配置来源与保存

### Buildroot

- 临时配置：`buildroot/.config`
- 固化配置：`bsp/configs/imx6ull_friedegg_emmc_defconfig`
- 保存临时配置：

```bash
./bsp/build_and_deploy.sh config save buildroot
```

- 丢弃临时配置，重新读取固化配置：

```bash
./bsp/build_and_deploy.sh config reset buildroot
```

### BusyBox

- 临时配置：`buildroot/output/build/busybox-*/.config`
- 固化配置：`bsp/configs/busybox.config`
- 修改配置：

```bash
make -C ./buildroot BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk busybox-menuconfig
```

- 保存配置：

```bash
./bsp/build_and_deploy.sh config save busybox
```

- 丢弃临时配置并重读 `bsp/configs/busybox.config`：

```bash
./bsp/build_and_deploy.sh config reset busybox
```

### Linux

- 临时配置：`buildroot/output/build/linux-custom/.config`
- 固化配置：`bsp/configs/linux.config`
- Buildroot 配置通过以下选项引用 BSP 中的 Linux 配置：

```bash
BR2_LINUX_KERNEL_USE_CUSTOM_CONFIG=y
BR2_LINUX_KERNEL_CUSTOM_CONFIG_FILE="$(BR2_EXTERNAL_BSP_PATH)/configs/linux.config"
```

- 修改配置：

```bash
make -C ./buildroot BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk linux-menuconfig
```

- 保存配置：

```bash
./bsp/build_and_deploy.sh config save linux
```

- 丢弃临时配置并重读 `bsp/configs/linux.config`：

```bash
./bsp/build_and_deploy.sh config reset linux
```

### 查看配置是否忘记固化

```bash
./bsp/build_and_deploy.sh config status
```

它会比较 Buildroot、BusyBox、Linux 当前临时配置和 `bsp/configs/` 中的固化配置。

## 配置边界

| 想增加或修改的能力 | 应配置的位置 | 说明 |
| --- | --- | --- |
| 内核驱动、文件系统、协议栈、built-in/module | `linux-menuconfig` | 影响 `zImage`、内核模块和内核 ABI |
| 用户态软件包、库、是否使用完整 `kmod` | `buildroot menuconfig` | 影响 rootfs 中的软件包 |
| BusyBox applet | `busybox-menuconfig` | 影响 BusyBox 提供的命令 |
| `modinfo`、`modprobe`、`depmod`、`insmod`、`lsmod`、`rmmod` | `busybox-menuconfig` | 当前 `bsp/configs/busybox.config` 已启用这些 BusyBox applet |

例如需要 `modinfo` 时，不需要改 Linux `zImage`。当前 BusyBox 已启用 `CONFIG_MODINFO=y`，目标板可直接使用：

```bash
modinfo /lib/modules/$(uname -r)/extra/ap3216c.ko
```

只有需要完整 kmod 工具集而不是 BusyBox applet 时，才去 Buildroot 中启用 `BR2_PACKAGE_KMOD`。

## 常用构建命令

### 首次或重新应用 Buildroot defconfig

```bash
make -C ./buildroot BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk imx6ull_friedegg_emmc_defconfig
```

### 下载源

固化下载源在 `bsp/configs/imx6ull_friedegg_emmc_defconfig`：

```bash
BR2_PRIMARY_SITE="https://sources.buildroot.net"
```

`buildroot/.config` 是当前生效的临时配置；修改 defconfig 后，需要重新应用一次才会生效：

```bash
./bsp/build_and_deploy.sh config reset buildroot
```

如果构建卡在某个 GitHub 下载，例如 `blake3-1.8.3.tar.gz`，先停止当前构建，再重新应用配置并重跑：

```bash
pgrep -af 'make BR2_EXTERNAL|wget|dl-wrapper'
kill <make-pid>
./bsp/build_and_deploy.sh config reset buildroot
./bsp/build_and_deploy.sh all
```

确认当前临时配置中的下载源：

```bash
grep '^BR2_PRIMARY_SITE=' buildroot/.config
```

### 全量重编并部署

```bash
./bsp/build_and_deploy.sh all
```

`all` 会执行 `make clean`，然后重新构建并部署 TFTP 与全量 NFS rootfs。Buildroot `make clean` 不删除 `buildroot/.config`；`distclean` 才删除 `.config` 和下载目录。

### 只重编并部署 DTB

适合只改 `src/linux-friedegg/arch/arm/boot/dts/imx6ull-friedegg-emmc.dts` 或相关 DTSI 的情况：

```bash
./bsp/build_and_deploy.sh dtb
```

脚本会从 `buildroot/output/build/linux-custom` 编译 `imx6ull-friedegg-emmc.dtb`，复制到 `buildroot/output/images/`，再部署到 TFTP。

### 只重编并部署 zImage

```bash
./bsp/build_and_deploy.sh zimage
```

该命令执行 Buildroot 的 `linux-rebuild`，然后只复制 `zImage` 到 TFTP。

### 只重编驱动并增量部署到 NFS

```bash
./bsp/build_and_deploy.sh drv ap3216c
./bsp/build_and_deploy.sh drv ov5640_drv
```

脚本会执行：

```bash
make -C ./buildroot BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk <pkg>-dirclean
make -C ./buildroot BR2_EXTERNAL=../bsp BR2_PACKAGE_OVERRIDE_FILE=../bsp/local.mk <pkg> -j$(nproc)
```

然后读取该包构建目录中的 `.files-list.txt`，只把该包安装到 `output/target` 的文件同步到 NFS。例如 `ap3216c` 会同步 `ap3216c.ko`、`ap3216cApp` 和 `modules.*` 索引文件，不再解包整个 `rootfs.tar`。

### 只重新部署全量 NFS rootfs

```bash
./bsp/build_and_deploy.sh rootfs
```

该命令会执行 Buildroot 默认构建并用 `rootfs.tar` 全量刷新 NFS。

## 版本验证

`verify` 的核心不是直接读取板子内存里的二进制，而是验证可复现链路：

- `zImage`/DTB：比较 `buildroot/output/images/` 与 TFTP 目录中的文件 hash，确认板子下次通过 TFTP 拿到的就是当前构建产物。
- `.ko`：比较 `buildroot/output/target` 与 NFS rootfs 中对应 `.ko` 的 hash，确认板子从 NFS 看到的模块就是当前构建产物。
- `.ko` 内核匹配：读取 `.ko` 的 `vermagic`，确认它以当前 Linux `kernelrelease` 开头。
- `.ko` 源码匹配：`drv <pkg>` 会生成 `buildroot/output/images/manifests/<pkg>.manifest`，记录驱动源码目录 hash、`.ko` hash、`srcversion`、`vermagic`、git commit/dirty 状态；`verify ko <pkg>` 会重新计算源码目录 hash，判断 `.ko` 是否来自当前源码。
- `zImage` 源码匹配：`zimage`/`all` 会生成 `buildroot/output/images/manifests/zimage.manifest`，记录 Linux 源码 git commit 和 dirty hash；`verify zimage` 会检查当前 Linux 源码是否又变过。
- DTB 源码匹配：`dtb`/`all` 会生成 `buildroot/output/images/manifests/dtb.manifest`，记录目标 DTS/DTSI hash；`verify dtb` 会检查当前 DTS 是否又变过。

注意：运行中的内核不会暴露完整 `zImage` hash，运行中的设备树也不一定保留原始 DTB hash。因此“板载 zImage/DTB 与源码一致”的可靠做法是：确认 U-Boot 从指定 TFTP 文件启动，主机侧验证 TFTP 文件与构建产物一致，再上板用 `uname -r`、`/proc/device-tree` 和测试属性做交叉确认。

### 一键验证

```bash
./bsp/build_and_deploy.sh verify all
```

验证内容包括 TFTP 中的 `zImage`/DTB hash，以及已启用本地驱动包在 NFS 中的文件 hash。

### 验证 zImage 或 DTB

```bash
./bsp/build_and_deploy.sh verify zimage
./bsp/build_and_deploy.sh verify dtb
```

这会比较 `buildroot/output/images/` 与 TFTP 目录中的文件 `sha256sum`。`verify zimage` 还会检查当前 Linux 源码 git 状态是否与最近一次 `zimage`/`all` 构建时一致；`verify dtb` 还会检查当前目标 DTS/DTSI hash 是否与最近一次 `dtb`/`all` 构建时一致。

### 验证驱动 `.ko`

```bash
./bsp/build_and_deploy.sh verify ko ap3216c
./bsp/build_and_deploy.sh verify ko ov5640_drv
./bsp/build_and_deploy.sh verify ko ap3216c.ko
```

验证内容：

- `.ko` 所在模块目录与 `make -C buildroot/output/build/linux-custom kernelrelease` 一致。
- `modinfo -F vermagic` 以当前 kernelrelease 开头。
- `modinfo -F srcversion` 可读取。
- `output/target` 与 NFS 中对应 `.ko` hash 一致。
- 如果该驱动通过 `drv <pkg>` 构建过，还会比较源码目录 hash 与 manifest 中记录的 hash。

### 验证某个包的 NFS 同步状态

```bash
./bsp/build_and_deploy.sh verify nfs-pkg ap3216c
./bsp/build_and_deploy.sh verify nfs-pkg ov5640_drv
```

该命令根据包 `.files-list.txt` 比较 `buildroot/output/target` 与 NFS 中的文件 hash，适合确认驱动增量部署是否生效。

### 实操：验证板载 zImage 与源码一致

主机侧先重新构建并部署 zImage：

```bash
./bsp/build_and_deploy.sh zimage
./bsp/build_and_deploy.sh verify zimage
```

查看本次构建记录：

```bash
cat buildroot/output/images/manifests/zimage.manifest
sha256sum buildroot/output/images/zImage "$HOME/linux/tftp/zImage"
make --no-print-directory -s -C buildroot/output/build/linux-custom ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- kernelrelease
```

预期：

- `verify zimage` 通过。
- `buildroot/output/images/zImage` 与 `$HOME/linux/tftp/zImage` 的 hash 一致。
- `zimage.manifest` 中的 `kernel_git_commit`、`kernel_git_dirty_hash` 与当前源码状态一致。

目标板 U-Boot 中确认启动命令确实从 TFTP 加载这个 `zImage`：

```text
printenv serverip ipaddr bootcmd bootargs image zimage
```

变量名可能因 U-Boot 环境不同而不同，重点看 `bootcmd` 中是否包含类似：

```text
tftp ... zImage
bootz ...
```

上板启动 Linux 后检查：

```bash
uname -r
cat /proc/version
dmesg | head -n 30
```

`uname -r` 应与主机侧 `kernelrelease` 一致。如果只改了内核源码但没有改 `LOCALVERSION`，`uname -r` 可能不变，此时以主机侧 `verify zimage` 和 U-Boot TFTP 加载路径为准。需要做强可观察验证时，建议临时修改 `bsp/configs/linux.config` 中的 `CONFIG_LOCALVERSION`，或在内核启动路径加一条临时 `printk`，重新执行 `zimage` 后在 `uname -r` 或 `dmesg` 中确认。

### 实操：验证板载 DTB 与源码一致

主机侧先重新构建并部署 DTB：

```bash
./bsp/build_and_deploy.sh dtb
./bsp/build_and_deploy.sh verify dtb
```

查看本次构建记录和 TFTP hash：

```bash
cat buildroot/output/images/manifests/dtb.manifest
sha256sum buildroot/output/images/imx6ull-friedegg-emmc.dtb "$HOME/linux/tftp/imx6ull-friedegg-emmc.dtb"
```

目标板 U-Boot 中确认启动命令确实从 TFTP 加载这个 DTB：

```text
printenv serverip ipaddr bootcmd bootargs fdtfile fdt_addr
```

重点看 `bootcmd` 中是否包含类似：

```text
tftp ... imx6ull-friedegg-emmc.dtb
bootz ... - ...
```

上板启动后检查运行中的设备树：

```bash
dmesg | grep -i 'Machine model'
tr -d '\0' < /proc/device-tree/model
find /proc/device-tree -maxdepth 2 -type d | head
```

如果要验证某次 DTS 修改确实进入板子，推荐临时加一个不会影响驱动匹配的测试属性，例如在根节点加：

```dts
friedegg,dtb-test = "2026-05-10";
```

然后执行：

```bash
./bsp/build_and_deploy.sh dtb
./bsp/build_and_deploy.sh verify dtb
```

上板重启后读取：

```bash
tr -d '\0' < /proc/device-tree/friedegg,dtb-test
```

能看到 `2026-05-10`，说明运行中的 DTB 来自当前 DTS 构建。验证完后删除临时属性，再重新执行 `dtb`。

### 实操：验证板载 `.ko` 与源码一致

以 `ap3216c` 为例，主机侧重新编译并增量部署：

```bash
./bsp/build_and_deploy.sh drv ap3216c
./bsp/build_and_deploy.sh verify ko ap3216c
./bsp/build_and_deploy.sh verify nfs-pkg ap3216c
```

查看 manifest 和模块元数据：

```bash
cat buildroot/output/images/manifests/ap3216c.manifest
modinfo -F vermagic buildroot/output/target/lib/modules/*/extra/ap3216c.ko
modinfo -F srcversion buildroot/output/target/lib/modules/*/extra/ap3216c.ko
sha256sum buildroot/output/target/lib/modules/*/extra/ap3216c.ko "$HOME/linux/nfs/rootfs"/lib/modules/*/extra/ap3216c.ko
```

预期：

- `verify ko ap3216c` 通过。
- `.ko` 的 `vermagic` 以主机 `kernelrelease` 开头。
- `output/target` 与 NFS 中的 `.ko` hash 一致。
- `manifest` 中的 `source_hash` 与当前 `src/ap3216c_drv` 重新计算结果一致；如果源码在构建后又改过，`verify ko ap3216c` 会失败。

上板侧确认板子从 NFS 看到同一个模块：

```bash
uname -r
modinfo /lib/modules/$(uname -r)/extra/ap3216c.ko
sha256sum /lib/modules/$(uname -r)/extra/ap3216c.ko
```

把板上 `sha256sum` 输出与主机侧 NFS `.ko` hash 对比，应完全一致。加载验证：

```bash
lsmod
rmmod ap3216c
insmod /lib/modules/$(uname -r)/extra/ap3216c.ko
lsmod
dmesg | tail -n 80
```

如果模块已被其他驱动占用导致 `rmmod` 失败，先停止相关应用或重启后再验证。需要强可观察验证时，在驱动 probe/init 路径临时加一条 `printk`，重新执行 `drv ap3216c`，上板重新加载后在 `dmesg` 中确认。

## 新增驱动编译方法

### build-in

如果要把驱动编进内核，需要修改内核源码中的 `Kconfig`、`Makefile` 和 `bsp/configs/linux.config`，然后重新编译内核：

```bash
./bsp/build_and_deploy.sh zimage
```

### module `.ko`

推荐把外部驱动做成 Buildroot external local 包，并在包 `.mk` 中使用：

```make
$(eval $(kernel-module))
$(eval $(generic-package))
```

当前脚本支持新增 `./src/**_drv` 驱动的单独编译部署，但前提是这个目录必须注册成 BSP local 包。只把源码目录放到 `src/` 下面，Buildroot 不会自动识别。

#### 源码目录要求

最小目录结构：

```text
src/foo_drv/
├── Makefile
└── foo.c
```

驱动 `Makefile` 至少需要支持内核外部模块构建：

```make
obj-m += foo.o
```

如果还带用户态测试程序，建议 `Makefile` 额外提供 `app` 目标，例如：

```make
APP_NAME := foo_test
APP_SRC := foo_test.c

.PHONY: app
app:
	$(CC) $(CPPFLAGS) $(CFLAGS) $(APP_SRC) -o $(APP_NAME) $(LDFLAGS)
```

#### 注册新驱动包

只有 `.ko`，无测试程序：

```bash
./bsp/build_and_deploy.sh drv add foo_drv ./src/foo_drv
```

同时编译并安装测试程序到 `/usr/bin`：

```bash
./bsp/build_and_deploy.sh drv add foo_drv ./src/foo_drv foo_test
```

这个命令会自动生成：

- `bsp/package/foo_drv/foo_drv.mk`
- `bsp/package/foo_drv/Config.in`
- `bsp/Config.in` 中的 `source` 入口
- `bsp/configs/imx6ull_friedegg_emmc_defconfig` 中的 `BR2_PACKAGE_FOO_DRV=y`

然后重新应用 Buildroot defconfig：

```bash
./bsp/build_and_deploy.sh config reset buildroot
```

#### 单独编译并部署新驱动

```bash
./bsp/build_and_deploy.sh drv foo_drv
```

脚本会执行 `<pkg>-dirclean` 和 `<pkg>`，然后根据包 `.files-list.txt` 只同步该包文件到 NFS。对于新驱动，通常包括：

- `/lib/modules/$(kernelrelease)/extra/foo.ko`
- `/usr/bin/foo_test`，如果注册时提供了测试程序
- `/lib/modules/$(kernelrelease)/modules.*` 索引文件

#### 验证新驱动

主机侧：

```bash
./bsp/build_and_deploy.sh verify ko foo_drv
./bsp/build_and_deploy.sh verify nfs-pkg foo_drv
```

目标板侧：

```bash
uname -r
modinfo /lib/modules/$(uname -r)/extra/foo.ko
insmod /lib/modules/$(uname -r)/extra/foo.ko
lsmod
dmesg | tail -n 50
```

如果需要自动依赖解析，用 `modprobe foo` 前先确认 `/lib/modules/$(uname -r)/modules.dep` 已同步，且模块名和 alias 配置符合预期。

#### 手工创建包的方式

也可以手工创建 `bsp/package/<pkg>/`。新增包后，在 `bsp/configs/imx6ull_friedegg_emmc_defconfig` 中启用对应 `BR2_PACKAGE_xxx=y`，然后重新应用 defconfig：

```bash
./bsp/build_and_deploy.sh config reset buildroot
./bsp/build_and_deploy.sh drv <pkg>
```

## 脚本功能测试流程

以下流程分为主机侧和上板侧。会写入 TFTP/NFS 的步骤已明确标注。

### 0. 主机侧基线检查

```bash
./bsp/build_and_deploy.sh help
./bsp/build_and_deploy.sh drv list
./bsp/build_and_deploy.sh config status
```

如果 `config status` 提示 `Buildroot .config is not using bsp/configs/linux.config yet`，先迁移到新版配置来源：

```bash
./bsp/build_and_deploy.sh config reset buildroot
```

再次检查：

```bash
./bsp/build_and_deploy.sh config status
```

### 1. 全量构建部署测试

主机侧执行，会更新 TFTP 和全量 NFS：

```bash
./bsp/build_and_deploy.sh all
```

主机侧验证：

```bash
./bsp/build_and_deploy.sh verify zimage
./bsp/build_and_deploy.sh verify dtb
./bsp/build_and_deploy.sh verify nfs-pkg ap3216c
./bsp/build_and_deploy.sh verify nfs-pkg ov5640_drv
```

目标板 U-Boot 中确认启动参数使用 TFTP/NFS。具体变量名以你的 U-Boot 环境为准，常见检查命令：

```text
printenv ipaddr serverip bootargs bootcmd
```

上板启动后执行：

```bash
uname -r
mount | grep ' / '
ls /lib/modules/$(uname -r)/extra
modinfo /lib/modules/$(uname -r)/extra/ap3216c.ko
```

预期：

- `uname -r` 与主机 `make -C buildroot/output/build/linux-custom kernelrelease` 一致。
- rootfs 是 NFS。
- `/lib/modules/$(uname -r)/extra/` 下有 `ap3216c.ko`、`ov5640.ko`、`mx6s_capture.ko`。

### 2. DTB-only 测试

主机侧给 DTS 做一个可识别但安全的测试改动，例如只改注释或新增临时测试属性；确认能编译后再保留或撤销该改动。

```bash
./bsp/build_and_deploy.sh dtb
./bsp/build_and_deploy.sh verify dtb
```

上板重启后检查设备树是否更新。可用以下方法之一：

```bash
dmesg | grep -i 'Machine model'
find /proc/device-tree -maxdepth 2 -type f | head
```

如果你新增的是可读属性，可用：

```bash
tr -d '\0' < /proc/device-tree/<node>/<property>
```

### 3. zImage-only 测试

适合改了内核非 DTS 代码或 Linux 配置后验证。

主机侧：

```bash
./bsp/build_and_deploy.sh zimage
./bsp/build_and_deploy.sh verify zimage
```

上板重启后：

```bash
uname -r
dmesg | head -n 30
```

如果只改了内核代码但没有改 `EXTRAVERSION/LOCALVERSION`，`uname -r` 可能仍是 `4.1.15`，这种情况下以主机侧 TFTP hash 验证为准。

### 4. 驱动增量部署测试

主机侧先对驱动源码做一个可观察改动，例如增加一行 `printk`，然后：

```bash
./bsp/build_and_deploy.sh drv ap3216c
./bsp/build_and_deploy.sh verify ko ap3216c
./bsp/build_and_deploy.sh verify nfs-pkg ap3216c
```

上板侧如果旧模块已加载，先卸载：

```bash
lsmod
rmmod ap3216c
```

再加载新模块：

```bash
insmod /lib/modules/$(uname -r)/extra/ap3216c.ko
modinfo /lib/modules/$(uname -r)/extra/ap3216c.ko
lsmod
dmesg | tail -n 80
```

预期：

- `insmod` 成功。
- `modinfo` 的 `vermagic` 以当前 `uname -r` 开头。
- `dmesg` 能看到你新增的测试日志。

### 5. 新增驱动包测试

以 `foo_drv` 为例：

```bash
./bsp/build_and_deploy.sh drv add foo_drv ./src/foo_drv foo_test
./bsp/build_and_deploy.sh config reset buildroot
./bsp/build_and_deploy.sh drv foo_drv
./bsp/build_and_deploy.sh verify ko foo_drv
./bsp/build_and_deploy.sh verify nfs-pkg foo_drv
```

上板：

```bash
modinfo /lib/modules/$(uname -r)/extra/foo.ko
insmod /lib/modules/$(uname -r)/extra/foo.ko
lsmod
dmesg | tail -n 80
foo_test
```

如果驱动依赖设备树节点，还需要先执行 `dtb` 流程并重启开发板。

### 6. rootfs-only 测试

适合改了 BusyBox、Buildroot 包、rootfs overlay 后验证。

主机侧，会全量刷新 NFS：

```bash
./bsp/build_and_deploy.sh rootfs
```

上板侧重启或重新挂载 NFS 后检查：

```bash
cat /etc/inittab
ls -l /etc/init.d/S10mdev
busybox | head
```

如果只是更新普通文件，NFS 上可能即时可见；如果更新 init、BusyBox、库文件或模块索引，建议重启目标板。
