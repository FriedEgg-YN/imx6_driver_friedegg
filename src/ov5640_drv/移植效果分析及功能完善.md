# 移植效果分析及功能完善

## 前言

参考链接实现了 OV5640 驱动的移植，使其支持 RGB565 800*480@30fps 格式的输出，参考datasheet feature，其存在以下不足：

- ov5640.c 的 s_fmt() 无视用户请求的宽高，固定写 RGB565 并切到 800x480@30fps。
- s_parm() 只记录目标帧率和 capturemode，真正调用 ov5640_change_mode() 的代码被注释掉。
- sensor subdev 没有 .s_stream，而 CSI host 的 streamon/streamoff 会尝试调用它。
- 没有注册任何 V4L2 controls，brightness/hue/contrast/saturation/red/green/blue/ae_mode 只是结构体字段，没有接到控制接口。
- cropcap/g_crop/s_crop 是占位实现，没有实际裁剪。

调研发现 Linux mainline 有更成熟的实现：Linux mainline OV5640 driver: https://codebrowser.dev/linux/linux/drivers/media/i2c/ov5640.c.html

**拟参考之，学习当前实现的subdev框架，并进一步完善，更进一步地，拟通过 perf 等工具进行性能分析、优化**。

## OV5640 驱动框架剖析

OV5640 为一 i2c 设备，故通过 i2c bus 进行匹配，在 struct i2c_driver 中只实现了 remove 与 probe 的回调。

当前驱动的主要内容为 i2c bus 的probe、remove及subdev回调，后者具体包括电源控制、video参数读取/设置、可用图像尺寸/帧率枚举

### 私有struct ov5640

```c
struct ov5640 {
	struct v4l2_subdev		subdev;
	struct i2c_client *i2c_client;
	struct v4l2_pix_format pix;
	const struct ov5640_datafmt	*fmt;
	struct v4l2_captureparm streamcap;
	bool on;

	/* control settings */
	int brightness;
	int hue;
	int contrast;
	int saturation;
	int red;
	int green;
	int blue;
	int ae_mode;

	u32 mclk;   // clk frequency: 24M
	u8 mclk_source; // 0
	struct clk *sensor_clk; // clocks = <&clks IMX6UL_CLK_CSI>；clock-names="csi_mclk" in dts
	int csi;    // 用来说明该摄像头链接哪路csi，当前并未被实际使用

	void (*io_init)(void);
};
```

### probe

在 probe 中，主要工作包括：

- 获取并设置 pwdn、reset gpio(此处用的legacy GPIO编号接口，传递的是raw value)
- 获取并初始化 clk，将其保存到 ov5640_data
- 读取指定寄存器验证传感器是 ov5640
- 配置 ov5640_data 的 pix 和 streamcap，init_device() 会根据 ov5640_data 中的配置进行初始化
- 初始化 i2c v4l2 subdev 并 async register

注意，ov5640 中关键内容基本在 probe 过程都填到了 ov5640_data 结构体中，这是驱动的惯有写法，也方便在回调函数中通过 drvdata 获取这些资源。

### ov5640_subdev_ops

接下来看 probe 中 i2c v4l2 subdev 初始化做了什么。`v4l2_i2c_subdev_init(&ov5640_data.subdev, client, &ov5640_subdev_ops);`，该函数将 i2c_client 与 subdev 绑定在一起，并提供了一个 ops 回调表，其内容如下：

```c
static struct v4l2_subdev_ops ov5640_subdev_ops = {
	.core	= &ov5640_subdev_core_ops,
	.video	= &ov5640_subdev_video_ops,
	.pad	= &ov5640_subdev_pad_ops,
};
```

`struct v4l2_subdev_ops` 是 V4L2 sub-device 的总回调表。V4L2 按功能域把 subdev 回调拆成多个子表，host 侧通常通过 `v4l2_subdev_call(sd, video, s_mbus_fmt, ...)` 这类形式按类别分发；如果对应类别或具体函数指针为空，则表示该 subdev 不支持该能力。

| 回调表成员 | 对应功能域 | 主要语义 |
| --- | --- | --- |
| `core` | subdev 通用控制 | 负责电源、初始化、reset、debug register、控制项、私有 ioctl、事件订阅等通用能力。 |
| `tuner` | 调谐器 | 用于电视/收音机 tuner，例如设置频率、读取频率、设置 tuner 类型、modulator 参数。 |
| `audio` | 音频芯片 | 用于音频 clock、I2S clock、音频输入输出 routing、audio stream 控制。 |
| `video` | 视频流和 video-level 操作 | 负责 mbus 格式协商、帧率参数、stream 开关、模拟制式、裁剪、bus 配置等视频相关操作。 |
| `vbi` | 垂直消隐区数据 | 用于模拟视频中的 closed caption、teletext、sliced VBI/raw VBI 等数据处理。 |
| `ir` | 红外收发 | 用于带红外接收/发射功能的采集卡芯片，提供 rx/tx 参数和红外脉冲数据读写。 |
| `sensor` | sensor 专有补充接口 | 用于告知 host 需要跳过的顶部行数或起流后需要丢弃的前几帧。 |
| `pad` | media controller pad 级操作 | 面向 media graph 端口，负责枚举 mbus code、分辨率、帧间隔、pad 格式、selection、链路校验等。 |

*注：更多细节可看 v4l2-subdev.h 中暴露的接口*

具体实现参考源码，已补充注释。此处补充一些关键结构体的说明：

```c
struct v4l2_streamparm {
	__u32 type;
	union {
		struct v4l2_captureparm capture;
		struct v4l2_outputparm output;
		__u8 raw_data[200];
	} parm;
};

struct v4l2_captureparm {
	__u32 capability;
	__u32 capturemode;
	struct v4l2_fract timeperframe;
	...
};
```
- `v4l2_streamparm`
    - `type`：数据流/缓冲区类型，普通摄像头使用V4L2_BUF_TYPE_VIDEO_CAPTURE，合法类型还包括视频输出设备、视频overlay、VBI采集/输出等
    - `v4l2_captureparm`
        - `capability`：表示驱动支持哪些 stream 参数能力，当前包括V4L2_MODE_HIGHQUALITY和V4L2_CAP_TIMEPERFRAME，前者为高质量模式，后者为帧率/帧间隔参数
        - `timeperframe`：分为denominator和numerator，表示一帧时间
        - `capturemode`：与`capability`共用flag，表示当前mode

```c
/**
 * struct v4l2_mbus_framefmt - frame format on the media bus
 * @width:	frame width
 * @height:	frame height
 * @code:	data format code (from enum v4l2_mbus_pixelcode)
 * @field:	used interlacing type (from enum v4l2_field)
 * @colorspace:	colorspace of the data (from enum v4l2_colorspace)
 * @ycbcr_enc:	YCbCr encoding of the data (from enum v4l2_ycbcr_encoding)
 * @quantization: quantization of the data (from enum v4l2_quantization)
 */
struct v4l2_mbus_framefmt {
	__u32			width;
	__u32			height;
	__u32			code;// 描述总线上传输的像素编码、位宽、字节顺序、打包方式
	__u32			field;// 场格式/隔行方式，当前V4L2_FIELD_NONE表逐行扫描，有些隔行输出sensor采用其他类型控制top/bottom field
	__u32			colorspace;
	__u16			ycbcr_enc;
	__u16			quantization;
	__u32			reserved[6];
};
```

### 疑问

1. 何用i2c_master API？能否使用regmap？如何权衡？

`i2c_master_*`直接、依赖少，但要自己处理endian、错误码、mask read-modify-write等，容易出现read helper返回寄存器值还是错误码能语义混乱

`regmap`语义统一，错误码清楚，但对 camera sensor 大量 volatile 寄存器来说 cache 通常要关掉；大寄存器表下载不一定明显更快；

*补充：regmap cache 的基本价值是：如果寄存器值主要由 driver 写入、硬件不会自己改，那么 driver 再读同一个寄存器时可以从 cache 返回，resume 后也可以 regcache_sync() 恢复状态。但 ov5640 很多自动曝光、增益等寄存器可能会修改，所以需要设置为REGCACHE_NODE更稳(除非确认部分寄存器硬件不会改)。同时由于ov5640寄存器地址不是连续的，且有mask，无法变成bulk_write，所以regmap只是能进行封装，未必能提升速率*

2. mainline 实现中使用pm_ops管理 set_power，和使用subdev.core中.s_power区别在哪？

.s_power 是 V4L2 子设备接口，调用者是 video bridge/pipeline；pm_ops 是设备模型接口，调用者是 PM core。

3. 为什么 platform_driver 中没有 init？



### 优化点记录

- 用的legacy GPIO编号接口，传递的是raw value，不现代，改用gpiod系列API
- s_power只关闭clk，是否应该pwdn
- `ov5640_set_register`中client未使用
- `ov5640_s_parm`只在 ov5640_data 中缓存，未实际修改 v4l2_streamparm 
- `ov5640_s_fmt`只强制RGB565+800*480@30fps，未能实现实际s_fmt功能
- `ov5640_enum_framesizes`实现只返回第0、1个width和height最大值，且将min设为max，不符合原始语义
- `ov5640_enum_frameintervals`可读性差，与`ov5640_enum_framesizes`及`ov5640_s_fmt`需要联合修改确保枚举出的值可用
- 当前ov5640_mode_info_data将帧率控制与分辨率组合在一起，导致有m*n中配置，是否能解耦成m+n种，但OV5640 帧率及分辨率并非独立(page 22 in datasheet)

综述所述，当前驱动只是正好能在800*480@30fps格式下工作，回调函数的实现一塌糊涂。

### 私有 struct mx6s_csi_dev

```c
struct mx6s_csi_dev {
    struct device *dev;                         /* 绑定的 platform device 的 struct device。 */

    struct v4l2_ctrl_handler ctrl_handler;      /* V4L2 控件处理器，本驱动当前未填充控件。 */

    size_t discard_size;                        /* 丢帧 buffer 的图像有效大小。 */
    struct mx6s_buf_internal buf_discard[2];    /* 两个内部队列节点，对应 CSI 双 buffer 槽。 */
    struct v4l2_async_subdev asd;               /* 描述异步等待的 OV5640 subdev。 */
    struct v4l2_async_notifier subdev_notifier; /* V4L2 async notifier，负责等待 sensor probe。 */
    struct v4l2_async_subdev *async_subdevs[2]; /* notifier 使用的 subdev 匹配表，以 NULL 结尾。 */
    bool csi_mux_mipi;                          /* true 表示 CSI 输入来自 MIPI CSI bridge。 */
    struct mx6s_csi_mux csi_mux;                /* MIPI 输入路径的 GPR mux 配置。 */
};
```

### probe

- 初始化私有结构体struct mx6s_csi_dev

- 注册/初始 v4l2_device、ctrl_handler、mutex、spinlock
- 分配 video_device, 初始化, 注册
	- 绑定 v4l2_device
	- 指定 fops, ioctl_ops, release, lock, vb2_queue
	- 注册(创建/dev/videoX节点)
- 注册 CSI IRQ handler
	- spinlock，清中断
	- 错误处理
		- 无active buffer
		- R下FIFO overflow || HRESP error
		- BIT_ADDR_CH_ERR_INT
	- DMA_TSF_DONE 处理
		- 此处 start_streaming 时会给两个 FB 槽
		- 如果两个同时完成直接跳过
		- 如果一个槽传输完成，把刚完成的 active buffer 还给 VB2，从 capture 队列取下一个 buffer，立刻写回同一个 FB 槽的 DMA 地址
- 注册 subdevs，此处变量名存在误导，已修改
	- 找到port节点下的endpoint节点(对应源码中port变量)
	- 利用port变量中的endpoint获取sensor_node(ov5640@3c)
	- 将sensor_node保存到async_subdevs，声明异步匹配
	- 初始化subdev_notifier，将async_subdevs传递给它，规定num_subdevs,bound,unbind，注册subdev_notifier
	- 当ov5640 subdev probe完成，of node与上面async_subdevs注册的匹配成功，就会回调bound函数，bound会将subdev绑定到私有结构体中；unbind会将其从私有结构体移除

### video_device::mx6s_csi_fops

#### mx6s_csi_open

- 获取 mx6s_csi_dev 
- mutex_lock_interruptible（适合用户态直接触发、等待可能变长、并且还没修改关键状态时可以安全放弃的路径，如open/read/write/mmap）
- **vb2_dma_contig_init_ctx(csi_dev->dev)**，***此处DMA配置的流程应该单独提取出来总结***
	- @dev 为执行DMA的设备对象，由于吧图像数据DMA写入内存的是CSI，故传CSI对应的dev
	- 作用：vb2_dma_contig_memops为内核中全局函数表[videobuf2-dma-contig.c (line 843)]，此代码创建与其配套使用的 alloc_ctx。前者是内存后端，意为VB2 buffer使用连续内存分配器，后者为此DMA-contig分配器要以 CSI 这个dev 为DMA主体分配buffer
	- 原理：vb2_dma_contig_init_ctx() 内部本质上只是分配一个小对象，然后保存 struct device *dev。用户态调用VIDIOC_REQBUFS时，VB2 core 会调用本驱动的 queue_setup()。本驱动把这个上下文交给 VB2：alloc_ctxs[0] = csi_dev->alloc_ctx（在 mx6s_videobuf_setup），vb2_dma_contig 的 .alloc 回调会从 alloc_ctx 里取出 dev，再调用 DMA API 分配 coherent DMA 内存
- 配置 vb2_queue并初始化
	- qype、io_modes、ops、buf_struct_size_timestamp_flags、lock
	- **q->mem_ops=&vb2_dma_contig_memops**
- 增加runtime PM使用计数保证寄存器可访问（当前未实际实现PM，只保留了框架），提高总线频率避免带宽不足
- 同时subdev s_power 1，退出低功耗
- csi_init
	- clk_enable, hw_reset
	- 配置CSI 基础输入时序、模块时钟、初始图像参数等
	- 刷新嵌入式 DMA 控制器的 RxFIFO 状态
	- 禁止 RxFIFO DMA请求

#### mx6s_csi_close

- 获取 mx6s_csi_dev
- mutex_lock，注意close没有使用interruptible的mutex
	- 否者close等待mutex时如果被打断，由于`v4l2_release()`调用`mx6s_csi_close()`时后者返回值会被忽略，无条件进行`video_put()`
	- 用户态看起来已经 close() 了，甚至可以重新 open("/dev/videoX")，但驱动内部状态可能还像“上一个打开者没完全退出”。这会导致引用计数泄漏、无法 runtime suspend、总线频率降不下来、下次打开初始化遇到旧状态等问题
- 释放 vb2_queue
- csi_deinit
	- hw_reset
	- 配置CSI 基础输入时序、模块时钟、初始图像参数等，**为什么此处还要csi_init_interface**
	- 禁止 RxFIFO DMA 请求
	- 关闭时钟
- subdev s_power 0, 进入低功耗状态
- **vb2_dma_contig_cleanup_ctx**
- 释放提高总线频率
- 减少runtime PM使用计数

#### mx6s_csi_read

- 获取 mx6s_csi_dev
- mutex_lock
- `vb2_read(&csi_dev->vb2_vidq, buf, count, ppos, file->f_flags & O_NONBLOCK)`, vb2_vidq在open中完成了初始化，buf为用户空间缓冲区，来自read(fd, buf, count)中的buf，count为字节数，ppos为文件偏移指针，最后为flag，非阻塞VB2在等待采集完成的buffer时不会睡眠等待，而是返回-EAGAIN，否则阻塞等待一帧完成
- unlock

*注：open中队列初始化时为`q->io_modes = VB2_MMAP | VB2_USERPTR;`，没有设置`VB2_READ`，故实际使用read会返回-EINVAL*

#### vb2_fop_poll

- poll是用户态`poll()`/`select()`/`epoll()`是调用的入口

### vb2_queue ops::mx6s_videobuf_ops

```c
static struct vb2_ops mx6s_videobuf_ops = {
	.queue_setup     = mx6s_videobuf_setup,
	.buf_prepare     = mx6s_videobuf_prepare,
	.buf_queue       = mx6s_videobuf_queue,
	.wait_prepare    = vb2_ops_wait_prepare,
	.wait_finish     = vb2_ops_wait_finish,
	.start_streaming = mx6s_start_streaming,
	.stop_streaming  = mx6s_stop_streaming,
};
```

`struct vb2_ops` 是 videobuf2 队列的 driver-specific 回调表。`v4l2_ioctl_ops` 处理用户态命令，而 `vb2_ops` 处理 buffer 生命周期：分配前确定大小、QBUF 前校验、QBUF 后交给驱动、STREAMON 时启动硬件、IRQ 完成后由驱动 `vb2_buffer_done()` 归还给 VB2、STREAMOFF 时停止 DMA 并回收所有未完成 buffer。

注意：vb2_ops 并非与相应用户空间命令一一对应，而是用户命令驱动 VB2 状态机，VB2 状态机再按需要调用驱动回调。目的是为了将“用户API”与“驱动硬件时序”解耦

| 回调 | 当前函数 | 当前状态 | 语义 |
| --- | --- | --- | --- |
| `.queue_setup` | `mx6s_videobuf_setup()` | 已实现 | 在 `VIDIOC_REQBUFS`/`VIDIOC_CREATE_BUFS` 路径中被 VB2 调用。当前驱动设置单 plane，plane 0 大小为 `csi_dev->pix.sizeimage`，allocator context 为 `csi_dev->alloc_ctx`；若用户未指定数量则默认 32 个，并受 `MAX_VIDEO_MEM` 限制。 |
| `.buf_prepare` | `mx6s_videobuf_prepare()` | 已实现 | 在 buffer 入队前被 VB2 调用。当前驱动把 plane 0 payload 设置为当前 `sizeimage`，并检查平面容量是否足够容纳一帧。 |
| `.buf_queue` | `mx6s_videobuf_queue()` | 已实现 | 在 `VIDIOC_QBUF` 成功 prepare 后被 VB2 调用。当前驱动用 `spin_lock_irqsave()` 把 buffer 按 QBUF 顺序挂入 `csi_dev->capture`，等待 `start_streaming()` 或 IRQ frame_done 路径装入 CSI FB1/FB2。 |
| `.wait_prepare` | `vb2_ops_wait_prepare()` | 通用 VB2 helper | VB2 在阻塞等待完成帧前调用。该 helper 释放 `vq->lock`，避免 `DQBUF`/read/poll 等睡眠等待时长期持有 `csi_dev->lock`。 |
| `.wait_finish` | `vb2_ops_wait_finish()` | 通用 VB2 helper | VB2 从阻塞等待返回后调用。该 helper 重新获取 `vq->lock`，恢复 ioctl/file-io 路径的互斥保护。 |
| `.start_streaming` | `mx6s_start_streaming()` | 已实现 | 在 `vb2_streamon()` 进入 streaming 状态时调用。当前驱动要求至少 2 个 queued buffer，对应 CSI FB1/FB2 双 buffer；同时分配 discard buffer，装载初始 DMA 地址，最后调用 `mx6s_csi_enable()` 启动 CSI。 |
| `.stop_streaming` | `mx6s_stop_streaming()` | 已实现 | 在 `vb2_streamoff()` 或队列取消时调用。当前驱动关闭 CSI，遍历 `active_bufs` 和 `capture`，把仍处于 active 的 buffer 以 `VB2_BUF_STATE_ERROR` 归还给 VB2，并释放 discard buffer。 |
| `.buf_init` | 无 | 可选补充 | buffer 第一次分配或 USERPTR 首次获取后的一次性初始化。当前 `struct mx6s_buffer` 只需要嵌入 `vb2_buffer` 和内部链表节点，未额外实现。 |
| `.buf_finish` | 无 | 可选补充 | buffer 每次 DQBUF 还给用户态前的收尾处理。当前帧序号、timestamp 和状态在 IRQ 完成路径处理，不需要额外 finish。 |
| `.buf_cleanup` | 无 | 可选补充 | buffer 释放前的一次性清理。当前 DMA 内存生命周期由 `vb2_dma_contig_memops` 管理，驱动没有额外私有资源需要释放。 |

当前 buffer 流向可以概括为：`REQBUFS -> queue_setup -> QBUF -> buf_prepare -> buf_queue -> STREAMON -> start_streaming -> CSI IRQ -> vb2_buffer_done -> DQBUF`。其中 `mx6s_capture.c` 自己维护的 `capture/active_bufs/discard` 三条链表，是 VB2 队列之外的硬件调度状态：`capture` 表示用户已排队但尚未装入硬件，`active_bufs` 表示已经写入 CSI DMA 槽位，`discard` 用于用户补 buffer 不及时的时候继续接收并丢弃帧。
