- 驱动侧已支持事件模式查询/统计/手动触发，应用侧新增 `irqdemo` 用于验证事件链路。
- 面试表达口径：已完成中断框架设计与可验证链路；硬件真实 IRQ 触发待板级连线/电平条件恢复后再补测。

### 推荐执行顺序（按此走即可）

1. 编译驱动和应用，确认无编译错误。
2. 加载模块并创建设备节点（若脚本已处理则直接用脚本）。
3. 先跑 `read` 模式确认基础 I2C 读数正常。
4. 再跑 `irqdemo` 验证事件框架：模式、统计量、手动触发链路。
5. 最后做压力回归（`lockstress` / `lockrace`），确认新逻辑未引入并发回退。

### 最小命令集（板上/交叉环境二选一）

```bash
# 方式A：使用现有一键脚本
./build_and_deploy.sh

# 方式B：手动
make
gcc -o ap3216cApp ap3216cApp.c
insmod ap3216c.ko
```

```bash
# 基础读数验证（确认总线与寄存器访问正常）
./ap3216cApp /dev/ap3216c read 500 10

# 事件链路验证（重点）
./ap3216cApp /dev/ap3216c irqdemo 500 20 5

# 并发回归验证（可选但建议）
./ap3216cApp /dev/ap3216c lockstress 4 200
./ap3216cApp /dev/ap3216c lockrace 6 3
```

### 结果判定标准（避免“跑了但不知道算不算通过”）

- `read` 模式可持续输出 ALS/PS/IR 且无明显 I2C 读失败日志。
- `irqdemo` 中可看到事件模式（硬件受限下预期为 `POLL_SIM`），统计值随时间增长。
- 手动触发后统计应出现对应增量，证明“应用 -> ioctl -> 驱动事件核心”链路可用。
- 压力测试期间无卡死、无明显内核告警、设备可重复打开关闭。

### 失败时优先排查（高频）

1. `insmod` 失败：先看内核版本与模块编译版本是否一致，再看 `dmesg`。
2. 无设备节点：检查驱动 probe 是否成功、主次设备号与节点创建逻辑。
3. `irqdemo` 统计不增长：先确认设备可正常读数，再确认 ioctl 命令号与头文件同步。
4. 并发模式异常：优先复查 `atomic` 打开计数与锁路径是否被新代码绕开。

### 下一阶段建议（面向“真实硬件IRQ闭环”）

1. 先板级确认 AP_INT 实际连线与电平域（SNVS/普通 GPIO 域），再落 DTS。
2. 用示波器/逻辑分析仪确认 AP_INT 在遮挡/接近事件时是否有边沿变化。
3. 硬件信号确认后，再启用真实 `request_threaded_irq` 路径并对比 `POLL_SIM` 统计行为。
4. 将真实 IRQ 验证结果补充到 `INTERRUPT_FALLBACK_GUIDE.md`，形成最终闭环文档。
