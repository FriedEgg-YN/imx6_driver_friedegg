# AP3216C 中断框架兜底方案说明（面试导向）

本文档说明：在板级硬件链路受限、真实中断信号无法稳定验证时，如何保留完整中断框架并通过轮询注入完成快速响应链路验证。

## 1. 背景与问题

本项目在 DTS 与引脚映射排查后，发现目标中断网络在当前硬件条件下表现为“软件可见持续低电平且不可拉高”。这会导致：

- 无法稳定观测真实中断沿/电平变化
- 无法仅靠硬件实测证明 IRQ 处理链路

如果直接放弃中断，会让工程结构与简历叙事都变弱。因此采用“框架保留 + 兜底验证”策略。

## 2. 方案目标

- 保留真实中断框架代码（IRQ 申请、线程化处理、统计）
- 增加轮询注入路径，复用同一事件核心处理函数
- 在硬件受限时仍可验证“快速响应链路”
- 后续硬件恢复时无需推翻架构，只需切回 `HW_IRQ`

## 3. 总体架构

统一事件核心函数：

- `ap3216c_event_core_handle(...)`

两条输入路径：

- `HW_IRQ`：真实 `request_threaded_irq` 回调进入核心函数
- `POLL_SIM`：`delayed_work` 周期轮询触发条件，命中后进入核心函数

统一触发策略：

- `PS` 接近阈值命中触发
- `ALS` 相邻采样变化量大于阈值触发

关键点：

- 两条路径共享同一统计与日志口径
- 避免“中断版一套逻辑、轮询版另一套逻辑”的维护风险

## 4. 模式切换策略

驱动启动时优先尝试 `HW_IRQ`：

- 成功：模式为 `HW_IRQ`
- 失败或不可用：自动降级 `POLL_SIM`

用户态可通过 ioctl 查询和切换当前模式，并可动态配置 `PS` 阈值、`ALS` 变化阈值和轮询周期。

## 5. 为什么这在工程上成立

- 工程关注的是“可演进架构 + 可验证行为”，不是单一验证手段
- 在硬件不可控阶段，轮询注入可以验证核心事件处理路径
- 硬件恢复后切回 `HW_IRQ`，业务层与统计接口不需要重写

## 6. 与真实中断的差异边界

`POLL_SIM` 与 `HW_IRQ` 的差异：

- 触发时机：轮询依赖周期，实时性弱于真实 IRQ
- 功耗与 CPU 占用：轮询更高
- 抖动特性：轮询抖动由调度周期决定

因此在文档与简历中应明确：

- 已完成中断框架设计与实现
- 在当前板级受限条件下，使用轮询注入完成链路验证
- 不宣称“硬件中断已实测稳定通过”

## 7. App 验证方法

使用 `irqcfg + irqdemo`：

```bash
./ap3216cApp /dev/ap3216c irqcfg 2 200 200 10
./ap3216cApp /dev/ap3216c irqdemo 30
```

观察点：

- 当前事件模式（`HW_IRQ`/`POLL_SIM`）
- `total/hw/poll/manual` 统计是否增长
- 日志来源是否与模式一致

切回真实中断：

```bash
./ap3216cApp /dev/ap3216c irqcfg 1 200 200
./ap3216cApp /dev/ap3216c irqdemo 30
```

## 8. 面试表达模板

“我把中断处理做成了统一核心函数，真实 IRQ 和轮询注入都走同一处理链路。在当前板级中断线不可控的条件下，我没有删掉中断设计，而是保留完整 IRQ 框架并用轮询注入完成验证，确保代码可迁移。后续硬件恢复时只需要切回硬件触发，不需要重写上层逻辑。”

## 9. 后续硬件恢复清单

- 修复中断线硬件链路（可测得有效电平变化）
- 启用并验证 `HW_IRQ` 模式
- 对比 `POLL_SIM` 与 `HW_IRQ` 的响应延迟
- 将默认模式切回真实中断
